# Implementation Report

## M0.3 — Production hardening & launch sanity (2026-04-28)

After M0.2 the real app was running on `tenxpros.com`, but the
configuration was development-grade: a placeholder `SESSION_SECRET`,
`APP_URL=http://localhost:3003`, and four demo users with documented
passwords (including an ADMIN) that worked on the public domain. M0.3
closes those gaps without disturbing the live deployment.

| `/opt/tenxpros/app/.gitignore` (new) | Excludes `node_modules/`, `.next/`, env files, build info. |

### Were real secrets committed?

**No.** Real values live only in `/opt/tenxpros/.env.production`,
which is `chmod 600`, owned by `ubuntu`, and matched by both
`/opt/tenxpros/.gitignore` and `/opt/tenxpros/app/.gitignore`. The
tracked `docker-compose.yml` references the file by path; it contains
no secrets.

### Demo-user policy (effective state)

- **Production (`ALLOW_DEMO_USERS=false`):** The four demo users
  exist as rows in the DB (their FKs are referenced by the M0/M0.1
  seed certificate), but their bcrypt password hashes are random and
  unguessable. Sign-in attempts with the documented demo passwords
  fail. The seed will not re-create them.
- **Local dev (`ALLOW_DEMO_USERS=true`):** The seed creates them and
  prints their well-known passwords to stdout. This is the engineer
  workflow only.

### Remaining risks / TODOs

- `.env.production` is on a single host, with no off-host backup
  strategy yet. If the disk dies, regenerate `SESSION_SECRET` (cookies
  invalidate, no data loss) and re-set `ADMIN_PASSWORD`.
- `SESSION_SECRET` rotation has no scheduled task. See
  [SECURITY_AND_COMPLIANCE.md](SECURITY_AND_COMPLIANCE.md#secrets) for
  the documented annual rotation procedure.
- The Next.js build still emits a warning that `pnpm start` doesn't
  use the standalone bundle — performance / image-size optimisation
  for a future pass; functional today.
- Demo certificate row in the DB still exists from the M0 seed (the
  demo professional's password is now scrambled, so it isn't
  exploitable, but the `/verify/<publicId>` URL is still live). Can
  be deleted manually if desired; not a security risk.

## M0.2 — Dockerised real-app rollout (2026-04-28)

The M0 / M0.1 passes left a built, lint-clean app on disk but no
running production surface — host port 3003 was unbound, the Caddy
block for `tenxpros.com` was returning 502, and the nginx placeholder
service was defined-but-not-running. M0.2 ships the real Next.js app
behind that port.

### What was built

- `app/Dockerfile` — multi-stage `node:20-bookworm-slim` image with
  corepack-managed pnpm 9.15.9. The runtime stage keeps the full app
  + `node_modules` so `pnpm db:deploy` and `pnpm db:seed` are runnable
  inside the container. CMD is
  `pnpm prisma migrate deploy && pnpm start`, so deploys are
  migration-safe by construction. Image-level `HEALTHCHECK` pings
  `/api/health`.
- `app/.dockerignore` — keeps build context tight (excludes
  `node_modules`, `.next`, `.env*`, `.git`, `tsconfig.tsbuildinfo`).
- `docker-compose.yml` rewritten:
  - Removed the `tenxpros-web` nginx placeholder service.
  - Added `tenxpros-app` (build: `./app`), mapped `3003:3000`, with
    in-compose `DATABASE_URL=postgresql://…@db:5432/tenxpros` and
    `depends_on: db (service_healthy)`.
  - Kept the `db` service untouched and the `tenxpros-db-data` volume
    intact.
- Stale Open Graph metadata fixed in `app/src/app/layout.tsx`
  ("…showcase, and **match**" → "…showcase, **connect**" + ecosystem
  one-liner) so social previews match the M0.1 boundary correction.
- Two new docs: [DEPLOYMENT_AUDIT.md](DEPLOYMENT_AUDIT.md) and
  updated [DEPLOYMENT.md](DEPLOYMENT.md).

### Issues encountered and how they were fixed

| Issue | Fix |
|-------|-----|
| Host port 3003 was held by a stray `pnpm next start -p 3003` from `/opt/tenxrole`, started by another local agent (codex) ~1 min before this rollout. Not the TenXRole production container (that's `tenxrole-app`, reached via Docker DNS). | Killed the stray PID. Production TenXRole was unaffected. |
| After `docker compose up -d`, the app container couldn't resolve `db:5432` because the existing `tenxpros-db` was still on the *previous* project network only. | `docker compose down && docker compose up -d`. The named volume `tenxpros-db-data` preserved all M0/M0.1 data through the recreate. |

# Implementation Report — M0.1 (2026-04-27)

## 1. What was built (in this pass)

Strategic correction: TenXPros was previously framed in the docs and
copy as a generic "AI adoption + visibility" platform that overlapped
with TenXRole on career-execution surfaces. M0.1 repositions TenXPros
as the **AI-adoption service / certification / talent-network layer**
that complements — and never duplicates — TenXRole (career management
product) and TenXOps (organisational AI adoption).

Concretely shipped:

- Four new docs that fix the boundary and the integration contract:
  - [`docs/ECOSYSTEM_BOUNDARIES.md`](ECOSYSTEM_BOUNDARIES.md)
  - [`docs/TENXROLE_INTEGRATION.md`](TENXROLE_INTEGRATION.md)
  - [`docs/TALENT_NETWORK.md`](TALENT_NETWORK.md)
  - [`docs/CUSTOMIZATION_SYSTEM.md`](CUSTOMIZATION_SYSTEM.md)
- Schema additions:
  - `TalentPoolStatus` enum + `ProfessionalProfile.talentPoolStatus`.
  - `TenXRoleConnection` model (per-pro consent + sync state).
  - `PromptPack` model (global and user-owned prompt packs for the
    customisation system).
  - Expanded `EmployerRequestStatus` to nine workflow states; legacy
    values preserved for back-compat.
- Migration `20260427220600_ecosystem_boundary_update` and a re-seed
  that adds two **global** prompt packs (`pm-status-pack`,
  `career-positioning-pack`).
- Public UI copy updates — homepage, For Professionals, For
  Organisations, About, Footer.
- Refit of `/opportunities` (authenticated) as the explicit TenXRole
  connection panel (bidirectional payload preview + manual handoff
  today).
- App-nav label change: "Opportunities" → "TenXRole".
- Dashboard lifecycle step: "Showcase / Match" → "Showcase / Connect".

## 4. TenXRole relationship

Defined in [`TENXROLE_INTEGRATION.md`](TENXROLE_INTEGRATION.md):

- **Modes:** manual handoff (today), mock API (scaffolded), production
  REST/RPC (planned).
- **Outbound payload (TenXPros → TenXRole):** AI readiness score,
  certificate level + status + verifyUrl, evidence summaries, learning
  completion, coaching notes, target roles, skill gaps, recommended
  positioning, prompt-pack refs, employer visibility, talent-pool
  status, introduction history.
- **Inbound payload (TenXRole → TenXPros):** career path goals, job
  targets, opportunity history, application outcomes, repeated skill
  gaps, interview feedback, market signals, role demand, resume /
  profile status, networking progress.
- **Schema support:** `TenXRoleConnection` is one-to-one with
  `ProfessionalProfile`. Per-category consent flags
  (`shareReadiness`, `shareCertificate`, `shareWorkModes`,
  `sharePromptPacks`, `shareCoaching`) gate the outbound payload.
  `lastSyncedAt` tracks freshness. The actual auth/token storage is
  out of scope for this repo (lives in surrounding TenX infra).

## 5. Talent network addition

Defined in [`TALENT_NETWORK.md`](TALENT_NETWORK.md):

- **Per-professional state machine:** `TalentPoolStatus` enum —
  `NOT_VISIBLE → ELIGIBLE → VISIBLE → SHORTLISTED → INTRODUCED →
  INTERVIEWING → OFFER_DISCUSSION → HIRED | PAUSED`.
- **Per-request state machine:** expanded `EmployerRequestStatus` —
  `NEW → DISCOVERY → ROLE_DEFINED → SHORTLIST_PREPARING →
  SHORTLIST_SENT → INTERVIEWS_ACTIVE → CLOSED_HIRED | CLOSED_NO_FIT |
  PAUSED`. Legacy values (`IN_REVIEW`, `CONTACTED`, `FULFILLED`,
  `REJECTED`) preserved so any existing rows / forms keep working.
- **Discipline rules baked into the docs and copy:** no employment
  guarantees, no automated rejection, recommendations stay advisory,
  consent before introduction.

## 11. Known risks

- `TenXRoleConnection` ships with consent flags but no UI to edit
  them. Defaults are conservative (`shareReadiness`,
  `shareCertificate`, `shareWorkModes` true; `sharePromptPacks`,
  `shareCoaching` false), so this is safe by default.
- Legacy `EmployerRequestStatus` values stay in the enum to avoid a
  disruptive migration. New code should use the workflow values; a
  follow-up cleanup pass can drop the legacy values once existing
  rows have been migrated.
- `PromptPack.prompts` is `Json @default("[]")` — light validation;
  add a Zod schema before exposing user-owned packs in the UI.
- Copy edits across multiple pages — re-read marketing pages after
  any subsequent change to keep the ecosystem one-liner consistent.
