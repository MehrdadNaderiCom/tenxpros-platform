# Certification Framework

Certificates are **evidence-based**, not attendance-based. A professional
cannot complete a certificate by watching lessons; they have to map real
tasks, ship real evidence, complete scenario assessments, and pass a
human review.

## Levels

| Code | Title | Headline |
|------|-------|----------|
| `L1_AI_READY` | AI-Ready Professional · Foundation | Baseline AI literacy, risk awareness and task-to-work-mode mapping. |
| `L2_AI_ADOPTED` | AI-Adopted Professional · Practitioner | Using AI responsibly and productively in real role-specific work, with quality control. |
| `L3_AI_AUGMENTED` | AI-Augmented Specialist | Designs multi-step AI tool chains with measurable improvement and credible oversight. |
| `L4_AI_IMPLEMENTER` | AI Adoption Implementer | Takes a workflow from prompt to working pipeline; handoff-ready. |
| `L5_AI_LEADER` | AI Adoption Lead | Guides team adoption, designs training, operates within governance. |

> The original product spec listed four levels. The schema implements
> five (splitting *implementer* and *lead*). Both are valid signals;
> public surfaces show all five.

## Statuses

`DRAFT → PENDING_REVIEW → ISSUED → (EXPIRED | REVOKED)`

A certificate moves to `PENDING_REVIEW` when the professional submits
themselves on `/certificates`. An admin or reviewer transitions it to
`ISSUED` (or `NEEDS_REVISION` via comment, returning to draft).

## Requirements engine

`src/lib/certification/eligibility.ts` exposes:

```ts
evaluateLevel(level, inputs): { level, satisfied, total, ready, checks[] }
evaluateAllLevels(inputs): EligibilityResult[]
```

`inputs` is computed at request time from the professional's records:

| Input | Source |
|-------|--------|
| `diagnosticCompleted` | latest `AIReadinessDiagnostic` |
| `basicLiteracyModulesCompleted` / `rolePathModulesCompleted` | `LessonCompletion` count |
| `tasksMapped` / `tasksClassified` | `ProfessionalTask` + `TaskAIClassification` count |
| `evidenceCount` | `EvidenceArtifact` count (status APPROVED/SUBMITTED) |
| `scenariosCompleted` / `advancedScenariosCompleted` | `ScenarioSubmission` count |
| `riskAwarenessPassed` | diagnostic `riskAwareness >= 3` |
| `reviewerApproved` | any `Certificate.status = ISSUED` |
| `productivityImprovementEvidence`, `implementationDesignSubmitted`, `oversightDemonstrated`, `teamAdoptionPlan`, `enablementMaterials`, `governanceScenario`, `guidedOthersEvidence`, `leadershipEvidence` | flags derived from evidence type / reviewer notes (planned) |

The dashboard shows an at-a-glance eligibility row for L1 and L2; the
`/certificates` page shows the full per-level checklist.

## Public verification

Public route: **`/verify/[publicId]`**

`publicId` is a 12-char `TXP-XXXXXXXX` token generated by
`generatePublicCertificateId()` in `src/lib/utils.ts`.

The verification page shows:

- name and headline of the holder
- certificate level
- issue date and expiration date
- verification status (issued / pending / expired / revoked)
- role focus
- evidence categories completed
- assessment dimensions passed
- the disclaimer below

> A TenXPros certificate verifies completion and evidence review *within
> the TenXPros framework*. It does not represent external accreditation
> unless explicitly stated.

Revoked certificates show the revocation reason; expired certificates
show the expiration date and remain queryable.

## Issuance flow

1. Professional reaches eligibility on `/certificates` and clicks
   *Submit for review*.
2. `Certificate.status` becomes `PENDING_REVIEW`.
3. Admin/reviewer opens `/admin/certifications/[id]`, reviews evidence
   and the eligibility checklist, and either issues or sends back.
4. On issue, `publicId` is generated, `verifyUrl` is set,
   `issuedByReviewerId` is recorded, and an audit log entry is written.

## Anti-fraud notes

- Certificates are tied to `ProfessionalProfile`, not just `User`, so
  removing the auth identity does not orphan an issued certificate.
- Public verification reads only `publicId`; `Certificate.id` is
  internal-only.
- Revocation is non-destructive: status changes; `revocationReason` is
  required for the public verification page to render.

## Customising for cohorts (future)

The framework is intentionally general so that cohort-specific or
sponsor-specific badges can be added without schema changes — by adding
a `programKey` system setting and reading it on the verify page.
